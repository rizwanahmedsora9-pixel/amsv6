# "Database is busy" / "database problems" — what was happening and what changed

## The short version
Every save of a direct sale rebuilt the **entire** profit/FIFO history to price
the one material being sold, and it did that **while holding SQLite's write
lock**. On PythonAnywhere's rollback-journal setup that means: for the whole
duration of one save, every other cashier is locked out. Two people saving at
the same moment → the second one gets *"database is locked"*.

Two separate defects were involved, and both are now fixed.

## Defect 1 — the save itself did the expensive work inside the lock
`BEGIN IMMEDIATE` was taken at the top of `add_direct_sale`, and only ~2.2 s
later did the first INSERT happen. Measured on a realistic database
(8 materials, 14.5k GRN lots, 18k sale lines, PA-style DELETE journal):

| | POST | write lock held |
|---|---|---|
| before | 2,613 ms | ~2.2 s |
| after  | 1,146 ms | ~0.9 s |

On a bigger, real-world database the full replay reached **15.2 s** in one
measurement — longer than the whole 15 s `busy_timeout`, so that save alone
guaranteed every other user saw a lock error.

What changed:

* `_Projection(..., fifo_only=True, material_scope=[...])`
  (`app/services/profit_loss.py`) — posting no longer loads/derives the parts
  of the projection that cannot affect a GRN lot balance (client settlement
  maps, per-line discount resolution, payments, pending bills, delivery
  rent/driver rows) and only replays the materials the document contains.
* `build_fifo_snapshot(..., material_scope=...)`
  (`app/services/grn_consumption.py`) and `_expand_chargeable_items_fifo`
  (`app/services/sales_core.py`) derive that scope from the document's own
  lines, so the **edit** path gets the same benefit.
* A scoped replay is **byte-identical** for the materials in scope. A GRN lot
  belongs to exactly one material and the FIFO replay never mixes materials,
  so it is exactly separable. Verified: 1,837 / 3,619 / 5,504 / all 14,542 lot
  balances identical, and identical FIFO layers (ids, quantities and per-lot
  rates) at qty 1 / 7 / 250 for every scope tried.
* Empty or unusable scope falls back to a **full** replay, never to a partial
  one, so a save can never price against half a lot queue.

## Defect 2 — the second saver failed instantly instead of waiting
SQLite's `BEGIN IMMEDIATE` raises *"database is locked"* immediately and does
**not** consult `busy_timeout` for that first acquisition. So two people saving
together was a hard error, not a queue.

`app/services/errors.py` now has `begin_write_transaction()`: it retries the
`BEGIN` (rolling back between attempts) for up to ~20 s, preserving the
serialisation it exists for, and if the lock really is stuck it flashes
*"The database stayed busy … Nothing was saved … please press Save again"*
with the form draft kept, instead of a 500.

Reproduced and verified with 4 simultaneous saves on a DELETE-journal copy:

| | result |
|---|---|
| before | 3 saved, **1 failed "database is locked"** |
| after | **4 saved, 0 failures** |

## Also fixed in this pass (each was a *write* on a page that only reads)
* `/grn`, `/direct_sales`, `/bookings`, `/payments` inserted a row into
  `bill_counter` on every page view (always rolled back, so it re-locked every
  time). Now read-only.
* `/cash_flow` ran `CREATE UNIQUE INDEX … ` + commit on every view. Now once.
* The due-bill reminder poll wrote `alerted_at` + committed **from every open
  tab every 15 s**. Now a pure read; the browser ACKs only what it actually
  showed (`POST /api/notifications/due/ack`).

## Verification
* `tests/run_all.py` → 12 + 25 = 37 passed, deep verification 22 passed, 0 failed
* `audit_chain.py` → 38 passed, 0 failed
* `audit_dedupe.py` → duplicates still rejected, stock/ledger consistent
* 4-reader + writer soak on a DELETE-journal copy → **0 errors, 0 500s**
* Posting/report FIFO parity → identical lot balances and layers

## What is left (not lock-related)
1. `/grn` (1.05 MB) and `/ledger/2` (13 MB) are very large single pages; under
   4-way load they take ~20 s. Pagination is the fix — that is page weight, not
   a lock.
2. `Material` master price is still used as a fallback when no GRN lot has been
   received yet (pre-purchase placeholder), so some older lines show a NULL
   frozen cost.
