## 2. The two retractions (read this first)

**F-06 — "No CSRF protection" — WITHDRAWN.** The build already enforces a session-bound token on every mutating route (`app/hooks.py::_protect_against_csrf`, wired as a `before_request` hook, with a templated `_csrf_token` on every form and an `X-CSRF-Token` path for fetch calls). The hook deliberately stands down when `app.config['TESTING']` is true — and my audit harness set `TESTING=True` and `WTF_CSRF_ENABLED=False`. I tested the app with its own seatbelt unclipped and then reported the seatbelt missing. Forcing the gate on (`AMS_CSRF_ALWAYS=1`) proves it works:

| Request | Result |
|---|---|
| `POST /add_payment`, no token | **HTTP 400** — `{"error": "Invalid or expired form token…"}`, **0 rows created** |
| `POST /add_payment`, session token | HTTP 302, receipt saved (1 row) |

**F-09 — "'No charges on this GRN' flash after charges were saved" — WITHDRAWN.** The string lives in `templates/grn_wizard.html` as the **empty-state** of the Expenses tab (`<div … id="grnChargesEmpty" {{ 'hidden' if charge_rows }}>`). My page-text scrape caught that hidden alert and I attributed it to the post-save flash. The flash was always "GRN added successfully!" and the charge was always saved. Re-verified: the 5,000 loading cost is stored as a `grn_charge` row, capitalised to 122.50/unit, and listed on the GRN.

I also **softened one severity**: F-11's "the booking receivable is never settled" was wrong — a booking balance for *delivered* goods is correctly a receivable. What was genuinely missing was the cost basis on the delivery document, which is what got fixed.

Everything else in the register held up under re-test.

## 3. What changed, finding by finding

### F-01 · A return now settles the bill it came from (HIGH)
- **Root cause:** `MaterialReturn` had no reference to a sale; the settlement projection always walked the client's open bills oldest-first.
- **Fix:** new `material_return.source_sale_id` / `source_bill_no` (auto-migrated by `_ensure_model_columns`, no manual SQL). The return form takes an optional **"Against Sale Bill"**; when it is blank the server picks the **newest sale to that client that contained the returned material and still has an open bill** — never simply the oldest. `_apply_settlement_to_pending_bills_for_client()` now takes `target_sale_id`/`target_bill_no` and settles that bill first, FIFO only for any remainder. The `rebuild_pending_bills()` replay reads the same link, so the allocation survives a rebuild.
- **Re-test:** bill A 1,500 / bill B 1,600; returning B's goods (10 × 160) → **B = 0, A = 1,500 untouched** (the audit's failing case settled B's credit onto A and left B open). Auto-detect case: bill C 17,000 → 16,150 after a 5 kg return.
- Files: `app/blueprints/sales/returns.py`, `app/services/void_rebuild.py`, `models/sales.py`, `templates/material_returns.html`.

### F-02 · Dashboard "Daily Due" keeps the delivered booking's value (HIGH)
- **Root cause:** `max(0, booking.amount - client_total_undelivered)` — one booking's undelivered balance cancelled another booking's delivered value.
- **Fix:** new `_booking_undelivered_by_booking()` maps undelivered value **per booking**; each booking withholds only its own.
- **Re-test:** delivered booking (16,000, 5,000 advance) + two undelivered bookings → Daily Due **31,100** (delivered charge 36,100 − money in 5,000); the tile equals the engine exactly.
- Files: `app/services/financial_ledgers.py`.

### F-03 · "Undelivered Bookings" shows the value once (HIGH)
- **Root cause:** the client's total was added inside the per-booking loop → 3 bookings × 30,000 = 90,000.
- **Fix:** accumulate the per-booking value instead.
- **Re-test:** three bookings (one delivered, two undelivered) → tile **30,000** = client ledger **30,000**.
- Files: `app/services/financial_ledgers.py`.

### F-04 · One definition of "what the customer owes" (HIGH)
- **Root cause:** `build_current_payables()` summed pending bills including undelivered bookings, while the client ledger held them outside the net balance.
- **Fix:** the payables projection now withholds the client's undelivered booking commitment, **discloses** it (`total_booking_commitment`, printed under the total: "Plus Rs. X of undelivered booking commitments (not a receivable)"), and the dashboard's Total Outstanding inherits the corrected figure because it reads the same projection.
- **Re-test:** dashboard **28,650** = Current Payables **28,650** = client ledger net **28,650** on the same day (the audit had 48,222 / 18,222 / 15,322). Commitments reported separately.
- Files: `app/services/financial_ledgers.py`, `templates/unpaid_transactions.html`, `app/blueprints/reports/_profit_unpaid_transactions_page.py`.

### F-05 · Daily Breakdown counts money, not credit notes (HIGH)
- **Root cause:** the tile summed every `Payment` row.
- **Fix:** reuse the shared `_is_cash_receipt()` predicate, total return credits separately, disclose them in the tile caption, and relabel the tile **"Cash Receipts"**.
- **Re-test:** with 3,950 of return credits on the day the tile reads **Rs 0.00 client receipts** and the caption says *"Rs. 3,950.00 of return credits excluded"* — the audit's tile would have read 3,950.
- Files: `blueprints/inventory/daily.py`, `templates/daily_transactions.html`.

### F-07 · Void means void; delete is a deliberate act (HIGH)
- **Root cause:** `/void_transaction/<type>/<id>` was an alias for the hard-delete service, so a "void" destroyed the document, its items, its stock entry and its bill number.
- **Fix:** `/void_transaction` now dispatches to the existing soft-void helpers for **DirectSale, Booking, Payment, MaterialReturn, GRN and Entry**; it **requires a reason**, writes `transaction.void.<type>` with the reason to `audit_log`, and keeps the document. `/delete_transaction` survives for drafts but demands a typed **DELETE** confirmation. Every UI button that used to say "Permanently delete" now voids with a reason prompt. One real bug surfaced while testing the soft path and was fixed too: **voiding a receipt did not give the customer their bill back** — the void now rebuilds the client's pending bills (`rebuild_pending_bills`) so the invoice reopens.
- **Re-test:** sale 2,800 voided → row kept with `is_void=1` and bill number `SB-SL-1005`, stock restored 470→490, receivable released, `audit_log: transaction.void.DirectSale id=6, reason=customer cancelled the order`; no reason → refused; delete without typing DELETE → refused; receipt void → cash −300 **and** the receivable +300; entry void → stock +100.
- Files: `app/blueprints/sales/_bills_void_transaction.py`, `app/services/void_rebuild.py`, six templates.

### F-08 · Walk-in returns work (MEDIUM)
- **Fix:** the return form accepts a bill number as the customer reference; when no master row exists the sale's own customer name is resolved to a real account (reused, or created as `WC-…`), so the credit has an owner and the returnable-quantity cap still applies.
- **Re-test:** 10 kg returned against a cash sale → accepted, stock +10, client `Cash Customer` / `WC-CASHCUSTOM` created, return linked to `SB-SL-1000`.
- Files: `app/blueprints/sales/returns.py`, `templates/material_returns.html`.

### F-10 · Integrity Audit tells the truth and checks the screens against each other (MEDIUM)
- **Fix:** booking dispatches, cash-settled sales and source-linked movements are no longer reported as "Missing Pending Bill"; a new **Cross-report Reconciliation** block compares Current Payables with the client ledgers and each cash account's balance with its own transaction ledger.
- **Re-test:** **0 sync issues, 0 mismatches** on a dataset containing a booking delivery (previously 1 false positive and silence about three real disagreements).
- Files: `app/blueprints/misc/_wipe_system_report.py`, `templates/system_report.html`.

### F-11 · The delivery document records its cost (MEDIUM)
- **Fix:** booked dispatches freeze `cost_rate_at_sale` from the purchase lot at the moment of dispatch (only when a real lot rate exists — otherwise it stays NULL so the P&L keeps flagging a genuine estimate). Sale value stays 0 **by design** (fulfilment only; revenue and the receivable live on the booking bill) — that part is now documented rather than changed.
- **Re-test:** delivery line `cost_rate_at_sale = 100.00` (was NULL); COGS still reconciles to the cent.
- Files: `app/services/sales_core.py`.

### F-12 · Every stock movement names its document (MEDIUM)
- **Fix:** GRN receipts stamp `source_module='GRN'`, `source_table='grn'`, `source_id`; return movements stamp `source_table='material_return'`.
- **Re-test:** **0 entries without a source** (was 4).
- Files: `app/blueprints/ops/grn.py`, `app/blueprints/sales/returns.py`.

### F-13 · No phantom bill for a settled counter sale (LOW)
- **Fix:** `_sync_direct_sale_pending_bill` skips tracking when a cash sale has nothing left to collect.
- **Re-test:** no pending bill for the fully-paid cash sale; **0 zero-amount live bills** in the whole DB.
- Files: `app/services/void_rebuild.py`.

### F-14 · The cash tile says what it means (LOW)
- **Fix:** "Daily Cash Received" → **"Cash on Today's Trading"**, with the caption *"plus Rs. X separately-posted receipts = Rs. Y total cash in"*, and Total Outstanding now reads *"Real dues across open bills (undelivered bookings shown separately above)"*.
- Files: `templates/index.html`.

### F-15 · The retired GRN cost fields actually post (INFO)
- **Fix:** `loading_cost` / `freight_cost` / `other_expense` are translated into INVENTORY charge rows before the grid syncs (one costing mechanism, no silently ignored money).
- **Re-test:** `loading_cost=5000` with no charge grid → one `LOADING` charge row, landed cost **49,000 → 122.50/unit** (the audit's equivalent GRN ignored it entirely).
- Files: `app/blueprints/ops/grn.py`.

## 5. Deployment notes and residual risk

1. **Database:** the only schema change is two nullable columns on `material_return`. The app's own `_ensure_model_columns()` adds them on first boot — **no manual migration, no data rewrite**. Take a backup first anyway; that is what the backup tool is for.
2. **Behaviour changes an operator will notice (all intended):**
   - Delete buttons now **void** and ask for a reason; documents stay in the lists marked void.
   - `Permanent delete` needs the word **DELETE** typed.
   - The home tile is called "Cash on Today's Trading"; Total Outstanding no longer includes undelivered bookings.
   - A return can name the bill it is against (optional).
3. **Residual, deliberately not changed:**
   - Client receipts (`/add_payment`) still allocate to the oldest open bill unless a target is given — a *payment* is not tied to an invoice in the data model, only a *return* is now. If you want "pay this bill" behaviour, that is the next change.
   - A booking dispatch still records a zero sale value (fulfilment semantics); revenue and receivable live on the booking.
   - The audit's untested areas (loans, delivery rents, import/export, backups, roles, concurrency) are still untested — this pass fixed findings, it did not widen coverage.
4. **Not applied to production.** The fixed build is `AMSV5-2_FIXED/`; your live app and its database are untouched.
